The Problem

Computing is fragmented. NOVA unifies it.

Today a typical project uses Python for the AI pipeline, Go for the backend, TypeScript for the frontend, C for the performance-critical path, and bash to glue it all together. Five languages, five build systems, five ways to define a data type. Every time data crosses a language boundary, someone writes a serializer and hopes both sides agree.

NOVA replaces that stack with one language that compiles to C-speed native code, runs concurrent servers out of the box, and targets WebAssembly for the browser — so you define your data type once, write your logic once, and deploy anywhere.

The Model

Everything is three things.

NOVA's entire computational universe is built from three primitives. Master these, and you can express any program — for any target.

Values

Everything is a value: integers, strings, structs, lists, dicts, byte buffers, even channels themselves. You write x = 42 or p = Point(3.0, 4.0) and the compiler infers the type, picks the allocation strategy (stack or heap), and decides how to free it — all without a single annotation from you.

Processes

Write spawn { work() } and NOVA creates a lightweight green task. Each process has its own memory — they never share heap, so there are no data races. If your program uses only one process, the compiler erases all the isolation machinery: zero overhead, same as writing C.

Channels

Processes talk through channels: send(ch, data) and recv(ch). Data is deep-copied on send, so the sender and receiver never share state. The same channel abstraction works in-process, across threads, and over the network — you change the target, not the code.

// NOVA uses Result<T> instead of exceptions.
// A function either returns Ok(value) or Err(message).
// This makes errors VISIBLE in the code — you can't
// accidentally ignore them like you can with exceptions.

fn parse_age(s) -> Result<int>
    // try = if parse_int fails, immediately return its Err
    let n = try parse_int(s)

    // Additional validation on the parsed value
    if n < 0 or n > 150
        return Err("age out of range: {n}")

    // Success: wrap in Ok
    Ok(n)

fn main()
    // match forces you to handle BOTH outcomes.
    // The compiler won't let you forget the Err case.
    match parse_age("25")
        Ok(age)  => print("Valid: {age}")     // Valid: 25
        Err(e)   => print("Error: {e}")

    match parse_age("999")
        Ok(age)  => print("Valid: {age}")
        Err(e)   => print("Error: {e}")     // Error: age out of range: 999
// NOVA concurrency: green tasks + channels.
// No async/await. No colored functions. No mutexes.
// spawn = launch a lightweight task (like Go's go).
// channel = typed queue between tasks (like Go's chan).
// send() deep-copies the data — tasks NEVER share memory.

fn worker(id, ch)
    for i in range(0, 3)
        send(ch, "Worker {id} produced item {i}")

fn main()
    let ch = channel()            // create a channel
    spawn { worker(1, ch) }      // launch task 1
    spawn { worker(2, ch) }      // launch task 2

    // Collect all 6 results (2 workers × 3 items each).
    // recv() blocks until a value arrives — but only
    // parks this task, not the OS thread.
    for _ in range(0, 6)
        print(recv(ch))

//   ...

What's happening here:

fn greet(name) defines a function. Notice there is no type annotation on the name parameter — the compiler sees you pass "NOVA" (a string) at the call site and infers that name is a string. You never need to write name: string for this to work.

"Hello, {name}!" — every double-quoted string in NOVA supports {expr} interpolation. No f"..." prefix needed (unlike Python). To put a literal brace in a string, escape it: \{.

Compare to Python: Python needs f"Hello, {name}!" with the f-prefix. Forget the f, and you get the literal text Hello, {name}!. In NOVA, interpolation always works.

What's happening here:

type Point defines a struct with two fields. Each field has a lowercase type: x: float. This tells the compiler to use native 64-bit doubles, which compile to raw CPU (Central Processing Unit) fmul/fadd instructions — same speed as C.

Common mistake: Writing x: Float (capital F) makes the field dynamically typed. Math on dynamic fields goes through a slow dispatch path — roughly 150x slower. This is the #1 performance mistake new NOVA users make.

fn dist(a, b) — no type on a or b. The compiler traces the call dist(p, q) where p and q are Points, infers a: Point and b: Point, and generates native float math. Zero annotations, C-level speed.

fn Point.magnitude() — this is a method. The struct becomes self inside the body. Methods are defined after the type block, not inside it. No impl keyword needed.

What's happening here:

NOVA uses Result<T> for error handling instead of exceptions. A Result is either Ok(value) (success) or Err(message) (failure). The caller must handle both cases — the type system enforces it.

try is the shortcut. When you write let n = try parse_int(s), it means: "if parse_int returns Ok, unwrap the value into n. If it returns Err, immediately return that same Err from my function." One word replaces Go's 3-line if err != nil { return err }.

match handles both outcomes explicitly. Unlike Python's try/except, you can't accidentally forget to handle the error — the match requires arms for both Ok and Err.

Compare to Go: Go returns (value, error) tuples and hopes you check the error. NOVA's Result makes it impossible to use the value without first checking for errors.

What's happening here:

channel() creates a typed queue. spawn launches a green task (like Go's goroutine). send(ch, data) puts data into the channel. recv(ch) takes data out, blocking only the current task (not the OS (Operating System) thread).

The key insight: deep-copy on send. When worker 1 sends "Worker 1 produced item 0" into the channel, NOVA deep-copies the data. The two workers can never accidentally share or corrupt each other's memory. No locks, no mutexes, no data races — by construction, not by discipline.

No async/await coloring. In JavaScript or Rust, if a function is async, every caller must also be async. This "colors" your entire codebase. In NOVA, spawn and recv are regular function calls. Any function can use them without changing its signature.

Scale: NOVA green tasks use ~2KB of stack each. You can spawn 10,000 in ~100ms. The runtime schedules them across a thread pool — cooperative multitasking with work-stealing.

What's happening here:

import forge loads NOVA's built-in web framework. No pip install, no npm install, no package manager step — it ships with the compiler.

forge.get(app, "/todos", fn(req) ...) registers a GET route. The handler function receives a request and returns data. When you return a list of structs, Forge automatically serializes them to JSON. You don't call json.dumps() or JSON.stringify() — the struct IS the response.

body_as(req) does the reverse: it reads the HTTP (HyperText Transfer Protocol) request body as JSON and creates a Todo struct from it. If the JSON doesn't match the struct shape (missing field, wrong type), it returns an Err — and try automatically sends an HTTP 400 Bad Request back to the client.

The result: You write nova build api.nova and get a single ~1.6MB executable. No Docker, no runtime, no dependencies. Copy it to any machine and run it.

Compare to Python Flask: Flask needs Python installed, pip, a WSGI (Web Server Gateway Interface) server (gunicorn), and runs ~50-100x slower. The NOVA binary runs at C speed and serves directly.

What's happening here:

enum Shape defines a type that can be one of three variants: a Circle (with a radius), a Rect (with width and height), or a Triangle (with three sides). Each variant carries its own data. This is like Rust's enum or TypeScript's discriminated unions — but simpler to write.

match s inspects which variant s is and runs the corresponding arm. Each arm binds the variant's data to variables: Circle(r) binds the radius to r. The compiler ensures every variant is handled — if you forget Triangle, the program reports an error at runtime.

Why not if/else? You could write if is_circle(s) ... else if is_rect(s) ..., but match does three things better: it extracts the data in one step, it's exhaustive (you can't forget a case), and the compiler can optimize it to a jump table.

Multi-line arms: The Triangle arm shows how to do computation inside a match. Indent the body under the => and the last expression is the result.

What's happening here:

write_file("todo.txt", ...) creates (or overwrites) a file and writes the string to it. The \n characters create line breaks inside the file. This is the simplest way to save data — one function call, no file handles to manage.

read_file("todo.txt") reads the entire file back as a single string. For small files (under a few MB), this is the easiest approach. For large files, NOVA also has file_open + file_read_line for line-by-line reading that doesn't load everything into memory.

append_file adds text to the END of a file without erasing what's already there — perfect for log files where you keep adding entries.

mkdir_p("output/reports") creates nested directories in one call (like mkdir -p on Linux). list_dir(".") returns a list of all files and folders in the current directory.

Compare to Python: Python needs open("file", "w") as f: f.write(...) — a context manager with indentation. NOVA: one function call. Python needs os.makedirs("a/b", exist_ok=True). NOVA: mkdir_p("a/b").

What's happening here:

What are iterators? An iterator is a lazy sequence — it produces elements one at a time, on demand. Unlike a list (which stores all elements in memory at once), an iterator only computes the next element when you ask for it. This means you can process a billion items without using a billion items of memory.

iter_range(1, 21) creates an iterator that will produce numbers 1 through 20. No list is allocated — the iterator just remembers "I'm at 1, my end is 21." Each call to get the next element returns the next number and increments the counter.

iter_filter(it, fn(x) x % 3 == 0) wraps the range iterator with a filter. When you ask for the next element, it pulls from the range, checks x % 3 == 0, and only passes through multiples of 3. Non-matching elements are silently skipped.

iter_map(it, fn(x) x * x) wraps the filter with a transformation. Each element that passes through the filter gets squared.

iter_collect(it) pulls ALL remaining elements through the pipeline and collects them into a list. This is when the actual computation happens — everything before this was just setting up the pipeline.

Key insight: The entire pipeline (range → filter → map → collect) processes each element one at a time. No intermediate lists are created between steps. For large datasets, this saves enormous amounts of memory.

What's happening here:

What are tensors? A tensor is a multi-dimensional array of numbers. A 1D tensor is a vector ([1, 2, 3]). A 2D tensor is a matrix (a grid of numbers with rows and columns). A 3D tensor is a cube of numbers (used for images: height × width × color channels). Tensors are the fundamental data structure in AI (Artificial Intelligence) and ML (Machine Learning).

tensor_from_list([1.0, 2.0, ...], [2, 3]) creates a 2×3 matrix from a flat list. The first argument is the data (6 numbers), the second is the shape. The data fills row by row: row 0 = [1, 2, 3], row 1 = [4, 5, 6].

tensor_relu(x) applies the ReLU (Rectified Linear Unit) activation function: every negative value becomes 0, positive values stay unchanged. ReLU is the most widely used activation function in neural networks — it introduces non-linearity while being extremely fast to compute.

tensor_matmul(a, w) is matrix multiplication — the core operation in neural networks. A 2×3 matrix times a 3×2 matrix gives a 2×2 result. Each output element is the sum of products of a row from a and a column from w.

tensor_softmax(x) converts raw numbers into probabilities that sum to 1.0. Used in the output layer of classifiers: "83% cat, 12% dog, 5% bird."

Compare to Python: Python needs import torch or import numpy (external libraries, pip install, 100MB+ download). NOVA has tensors built in — zero dependencies.

What's happening here:

All cryptography in NOVA is written in pure NOVA — no C library dependencies like OpenSSL. Every algorithm passes standard KAT (Known Answer Test) vectors, meaning the output matches the official test values bit-for-bit.

sha256("Hello, NOVA!") computes the SHA-256 hash of a string. SHA-256 (Secure Hash Algorithm, 256-bit) takes any input and produces a fixed 64-character hexadecimal string. Even a tiny change to the input produces a completely different hash — this is used for password storage, data integrity checks, and blockchain.

hmac_sha256("secret-key", "message") computes HMAC (Hash-based Message Authentication Code). Unlike a plain hash, HMAC uses a secret key — so only someone who knows the key can produce (or verify) the hash. This is how JWT (JSON Web Token) tokens, API signatures, and webhook verification work.

base64_encode / base64_decode converts binary data to/from a text-safe format. Base64 uses only letters, digits, +, /, and = — safe to embed in JSON, URLs, or email. Not encryption — just encoding.

Available algorithms: SHA-256/384/512, MD5, HMAC, PBKDF2 (password hashing), HKDF (key derivation), AES-GCM (encryption), ChaCha20-Poly1305 (encryption), X25519 (key exchange), Ed25519 (digital signatures), ECDSA P-256, RSA verification. Full TLS (Transport Layer Security) 1.3 handshake crypto is also built in.

What's happening here:

NOVA channels work across the network — not just within a process. The same mental model ("send a value, the receiver gets an independent copy") works whether your tasks are on the same machine or on different servers across the internet.

remote_listen("0.0.0.0", 9000) starts listening for incoming network connections on port 9000. "0.0.0.0" means "accept connections from any IP address."

remote_accept(listener) waits for a client to connect. When a client connects, it returns a connection handle — similar to how receive(ch) waits for a value on a local channel.

remote_recv(conn) receives a value from the remote client. Under the hood, NOVA reads length-prefixed JSON from the TCP (Transmission Control Protocol) socket and deserializes it into a NOVA dict. You get a native NOVA value, not a raw string.

remote_send(conn, {"status": "ok"}) sends a NOVA dict to the remote peer. The dict is automatically serialized to JSON and sent over the network. The deep-copy semantics are the same as local channels — the receiver gets an independent copy.

Why this matters: In most languages, local code (result = compute(data)) and distributed code (response = http.post(url, json.dumps(data))) look completely different. In NOVA, you use the same send/recv pattern everywhere. Refactoring from local to distributed doesn't require rewriting your communication code.

What's happening here:

FFI (Foreign Function Interface) lets NOVA call functions written in C. This is how you use existing C libraries — decades of code for databases, graphics, hardware drivers, and more — without rewriting them.

extern fn pow(base: float, exp: float) -> float declares that a C function called pow exists. extern fn tells the compiler: "I am not defining this function — it lives in a C library. Here is its type signature so you can generate the correct calling code." NOVA links against the C standard library by default, so math functions like pow, sin, cos are available immediately.

@link("sqlite3") tells the linker: "Also link against the SQLite library." Without this, the linker would fail with "undefined reference" errors for sqlite3_open.

unsafe { ... } marks a block where NOVA's safety guarantees are suspended. Inside unsafe, you can allocate raw memory (alloc_raw), read/write at arbitrary offsets (ptr_read/ptr_write), and free memory manually (free_raw). This is necessary for C interop but dangerous if used incorrectly — a buffer overflow or use-after-free is possible inside unsafe.

Why unsafe exists: Rather than making the entire language unsafe (like C) or forbidding low-level operations entirely, NOVA lets you opt into unsafety in clearly marked blocks. You can grep for unsafe in any NOVA codebase to find every place where safety is suspended — making audits easy.

Under the Hood

The genius compiler — where all the complexity lives.

You write simple code. The compiler does everything else: infers types, manages memory, checks safety, and generates machine code that matches C.

The 5-stage compilation pipeline:

Stage 1 — Lexer + Parser: Your .nova source code is tokenized (split into words, numbers, operators, keywords) and parsed into an AST (Abstract Syntax Tree). NOVA uses indentation-based scoping (like Python) — no curly braces, no semicolons. The parser tracks indentation depth to determine which statements belong to which block.

Stage 2 — Type Inference (HM): The Hindley-Milner (HM) type inference engine walks the AST and assigns types to every expression — without you writing any. How? It creates "type variables" (unknowns) for each expression, then solves constraints. When it sees a + b where a was passed 5 (an integer), it unifies: a = int, and since + on int returns int, the result is int. The entire program is type-checked this way. If a conflict is found (you pass a string where an int is expected), the compiler gives you a helpful error with line numbers — not a cryptic template dump.

Stage 3 — AST → IR (Intermediate Representation): The typed AST is lowered to a flat, register-based IR. High-level constructs (for loops, match arms, closures) become simple sequences of instructions: load, store, call, branch. This IR is where optimizations happen — dead code elimination, constant folding, and escape analysis (determining whether a value can be stack-allocated instead of heap-allocated).

Stage 4 — IR → LLVM (Low-Level Virtual Machine) IR: NOVA's IR is translated to LLVM IR — the same intermediate format used by C (clang), Rust (rustc), and Swift (swiftc). LLVM then runs 50+ optimization passes: SROA (Scalar Replacement of Aggregates — breaks structs into individual variables), mem2reg (promotes stack allocations to registers), GVN (Global Value Numbering — eliminates redundant computations), loop vectorization (uses SIMD instructions), and more.

Stage 5 — Linking: The optimized LLVM output is compiled to object code and linked with nova_runtime.c — NOVA's C runtime. The runtime provides: the green task scheduler (M:N threading, work-stealing), the channel implementation (lock-free MPSC queues), the arena allocator (bulk allocation + bulk free, no GC tracing), the netpoller (epoll on Linux, WSAPoll on Windows), and built-in functions (print, len, read_file, etc.). The result: a single standalone binary.

Self-hosted: The NOVA compiler is written in NOVA. It compiles itself — nova_compiler.nova (~21,000 lines) is fed to gen3_test.exe (the previous generation), which produces gen4_test.exe (the current generation). Both produce identical LLVM IR output, proving the compiler is correct. This is called "bootstrap convergence" — if generation N and generation N+1 produce the same output, the compiler is verified.

What the numbers mean:

1.04× C on scalar struct math means NOVA is within 4% of C's speed — for code written with zero type annotations and zero manual memory management. The 4% gap comes from NOVA's uniform i64 ABI (Application Binary Interface) which prevents LLVM's SROA from fully decomposing struct arguments. A future native-ABI stage will close this.

~100ms for 10,000 green tasks means each task costs about 10 microseconds to spawn. Each task uses ~2KB of stack. By comparison, an OS thread typically uses 1–8MB of stack and takes 10–100× longer to spawn.

Honest about gaps: Float array access is currently ~120× slower than C because float elements are boxed for type-safety in the polymorphic runtime. Typed array specialization (S4 in the optimization roadmap) will close this gap by using native double* arrays when the compiler can prove the element type at compile time.

Reading the table — what each row means:

Native speed: NOVA and C both compile through LLVM to machine code — on scalar and struct benchmarks, NOVA runs at 0.98–1.04× of clang -O2. Go is "partial" because its compiler produces good but not LLVM-tier code. Python is interpreted and typically 50–100× slower than C for compute-bound work.

Memory safe: C has no safety — buffer overflows, use-after-free, and undefined behavior are the developer's problem. Rust enforces safety through a borrow checker (powerful but complex). Python's GIL (Global Interpreter Lock) blocks true parallelism — multiprocessing is a workaround, not a solution.

Minimal ceremony: Python and NOVA both require minimal boilerplate — no public static void main, no header files. Rust requires lifetime annotations, trait bounds, and impl blocks. C requires manual header management and forward declarations. Go sits in the middle — simple syntax but explicit error handling (if err != nil on every call).

No GC pauses: Languages with garbage collection (Go, Python, Java) periodically pause your program to free unused memory. These pauses can spike to milliseconds — unacceptable for real-time systems. NOVA uses per-request arena allocation (bulk free, no tracing) plus reference counting for long-lived data. No stop-the-world pauses.

One toolchain: NOVA's compiler binary is also the build tool, the LSP (Language Server Protocol) server, and the package manager. Rust has a similar "one tool" story with cargo. C requires separate compiler, build system (Make/CMake/Meson), and has no standard package manager. Python has pip, venv, setuptools, poetry, conda — and they often conflict.

What NOT to Do

Avoid these common pitfalls — NOVA is different from what you're used to.

DON'T: Use capital-letter types for struct fields

// WRONG — 150x slower!
type Point
    x: Float   // capital F = dynamic dispatch
    y: Float
// RIGHT — C-speed native float
type Point
    x: float   // lowercase = native 64-bit double
    y: float

Why: Lowercase float tells the compiler to use native 64-bit IEEE (Institute of Electrical and Electronics Engineers) 754 doubles — the CPU (Central Processing Unit) performs fmul/fadd directly. Capital Float makes the field dynamically typed, and every math operation goes through a type-check dispatch at runtime. The difference: ~150x slower.

DON'T: Use Python-style boolean operators

// WRONG — these are NOT valid in NOVA
if x > 0 && y > 0   // && doesn't exist
if !done           // ! doesn't exist
// RIGHT — use English words
if x > 0 and y > 0
if not done

Why: NOVA uses and, or, not — English words, not symbols. This is part of the "simpler than Python" goal. Python already uses these words; C/Java/Rust use &&/||/!. NOVA follows Python's choice here because it reads more naturally.

DON'T: Forget that string interpolation is always on

// WRONG — {name} will be interpolated!
let template = "Hello, {name}!"
// If 'name' is defined, it gets substituted.
// If 'name' is NOT defined, you get an error.
// RIGHT — escape braces to get literal text
let template = "Hello, \{name\}!"
// Prints literally: Hello, {name}!

Why: Unlike Python (which needs f"..." to activate interpolation), NOVA's double-quoted strings ALWAYS interpolate {expr}. This means you never forget the f prefix — but it also means you need \{ when you want a literal brace character (common in JSON templates or regex patterns).

DON'T: Use semicolons or curly braces for blocks

// WRONG — NOVA is indentation-based
fn greet(name) {
    print("Hello");
}
// RIGHT — indent defines the block, no semicolons
fn greet(name)
    print("Hello")

Why: NOVA uses significant indentation (like Python) — not curly braces (like C/Java/Rust) and not semicolons. Indentation defines scope: everything indented under fn greet(name) is inside that function. This eliminates an entire class of bugs ("which brace closes which block?") and reduces visual noise.

Get Started

Your first NOVA (Natively Optimized Versatile Architecture) program in 30 seconds.

1

Install

Clone the repo and build the compiler. It's self-hosted — the NOVA compiler is written in NOVA. The result is a single binary (~1.6MB), no runtime needed. You also need LLVM (Low-Level Virtual Machine) installed for the backend (clang + llc).

git clone nova-lang/nova
cd nova && ./build.sh

Prerequisites: LLVM 14+ (clang and llc in your PATH). On Windows, install via the LLVM installer. On Linux/macOS, apt install llvm clang or brew install llvm.

2

Write hello.nova

Create a file. No imports, no class, no semicolons, no public static void main. Indentation defines blocks (like Python). The main() function is the entry point — the compiler finds it automatically.

fn greet(name)
    print("Hello, {name}!")

fn main()
    greet("world")

Note: Use 4-space indentation (not tabs). {name} is string interpolation — always active, no f"..." prefix needed.

3

Compile and run

nova run compiles to LLVM IR (Intermediate Representation), links with the C runtime, and executes the resulting native binary. Or use nova build to produce a standalone executable you can ship anywhere.

nova run hello.nova
# → Hello, world!

nova build hello.nova
# → produces hello.exe (Windows) or hello (Linux)
# Single binary, no dependencies, copy and run anywhere

What just happened under the hood:

Step 1 — Parsing: The compiler reads your .nova file and builds an AST (Abstract Syntax Tree) — a tree representation of your program's structure. Function definitions, expressions, and control flow become nodes in the tree.

Step 2 — Type Inference: The Hindley-Milner (HM) type inference engine walks the AST (Abstract Syntax Tree). It sees greet("world") — you passed a string, so name must be a string. It sees "Hello, {name}!" — string interpolation on a string, returns a string. All types are inferred. You wrote zero annotations.

Step 3 — IR (Intermediate Representation) Generation: The typed AST (Abstract Syntax Tree) is lowered to NOVA's internal IR (Intermediate Representation) — a simpler, flat instruction set that's easier to optimize. Dead code is eliminated. Constants are folded. Unused abstractions are erased.

Step 4 — LLVM (Low-Level Virtual Machine) Codegen: The IR (Intermediate Representation) is translated to LLVM IR — the same format used by C and Rust compilers. LLVM's optimizer (50+ optimization passes including SROA, mem2reg, GVN, loop vectorization) produces highly optimized machine code.

Step 5 — Linking: The LLVM output is linked with nova_runtime.c (NOVA's C runtime — garbage-free arena allocator, green task scheduler, channel implementation, netpoller) to produce a standalone native binary.

Total time: For a small program, this entire pipeline runs in under 2 seconds. The result: a native binary that runs at C speed, with zero runtime dependencies.
